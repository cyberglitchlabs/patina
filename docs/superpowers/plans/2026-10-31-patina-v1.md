# Patina v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build Patina v1: a long-running Rust service that merges unreliable guide providers (Gracenote first) into one persisted master guide and serves well-groomed XMLTV feeds to Jellyfin.

**Architecture:** A pure-functional core (slot matching, merge, scoring) decides what changes; a `Store` trait (sqlx, SQLite default and Postgres) persists it; a shared fetch layer (budget, rate limit, backoff, circuit breaker, bad-window memory, raw cache) is the only code that talks to providers; a scheduler drives tiered refreshes; axum serves feeds, status, metrics and health; a janitor enforces retention.

**Tech Stack:** Rust (stable), tokio, axum, reqwest (rustls), sqlx (sqlite + postgres + migrate), serde + toml, tracing + tracing-subscriber (JSON), a Prometheus client crate, quick-xml, chrono + chrono-tz, proptest. Pick current stable versions when adding each crate; pin them.

**Spec:** `docs/superpowers/specs/2026-10-31-patina-design.md` (read it first; section numbers below refer to it).

## Global Constraints

- Package and binary name `patina`; not published to crates.io. License `MIT OR Apache-2.0` (files `LICENSE-MIT`, `LICENSE-APACHE`).
- Repo `github.com/cyberglitchlabs/patina`; image `ghcr.io/cyberglitchlabs/patina`, multi-arch (amd64, arm64), semver tags, pinned base images.
- SQLite is the default store; PostgreSQL is first-class. Migrations are embedded, automatic at startup, forward-only (never edit an applied migration); startup fails if one fails. Separate migration dirs: `migrations/sqlite/`, `migrations/postgres/`.
- Times are UTC internally; XMLTV output uses correct local offsets (timezone from config, default `America/Chicago`).
- Gracenote: `GET https://tvlistings.gracenote.com/api/grid` with `timespan=6` (the only proven value; `48` returned HTTP 400), browser-like User-Agent, tolerate HTTP 400 windows, honor `Retry-After` and 429. Default daily budget 150 requests per provider, hard stop. Image URL form `https://zap2it.tmsimg.com/assets/<thumbnail>.jpg`.
- Retention defaults: images 3 days after last referencing programme airs, raw responses 7 days, aired programmes 7 days after end, score/metrics history 90 days; janitor runs daily; disk-cap evicts oldest first.
- Config: env vars for simple settings, one TOML file (path from env var) for structured ones, env wins, strict validation, refuse to start on invalid config.
- Endpoints: `/healthz` always open; `/status` (JSON) and `/metrics` (Prometheus) behind optional bearer token; XMLTV feeds behind one optional URL token. Open by default.
- CI never contacts a real provider except a manually triggered workflow. Tests are fully offline.
- Code style: plain and conventional; the author has no Rust or SQL experience, so comment non-obvious logic and prefer simple constructs.

## Review Focus

Spec-implied conditions no obvious task test covers; each has a pinning test in the owning task (marked ★).

1. A crash-looping or restarting process must not reset the daily request budget (a restart storm must not become a request storm). ★ Task 6
2. XMLTV offsets across a daylight-saving change (US fall-back is 2026-11-01, the day after the design date). ★ Task 11
3. An HTTP 200 response that is empty, lacks a channel, or has a channel with zero events must not delete or shorten existing slots. ★ Task 8
4. Malformed provider events (end <= start, missing title, absurdly long text, duplicate events) are dropped and counted, never stored or crashing the run. ★ Task 5
5. XML-hostile and Unicode text in titles and descriptions (`&`, `<`, quotes, emoji, control characters invalid in XML 1.0) yields well-formed XMLTV. ★ Task 11
